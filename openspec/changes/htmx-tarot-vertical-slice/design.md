## Context

The current product has Django/Ninja models for cards, mentors, users, readings, and reading cards, but the reading service delegates spread/card selection to an LLM. `celestial-neutral` contains richer content and a useful structured contract, while `celestial-tg` contains a disconnected client flow. See proposal.md for the product motivation.

## Goals / Non-Goals

**Goals:**

- Establish Django as the single runtime and data authority for the first product slice.
- Support a complete no-JavaScript-first web reading with HTMX enhancements.
- Persist a draw before interpretation and retain it across retries.
- Create an explicit, secure boundary for later Telegram handoff.

**Non-Goals:**

- Restoring or extending Streamlit or Next.js as production clients.
- A paid token economy, social OAuth redesign, reading sharing, custom decks, or bot-created readings.
- Claiming predictive certainty or providing professional health, financial, or legal guidance.

## Decisions

### Django templates and HTMX are the launch web surface

Add a `web` application or equivalent template/view layer served by the existing Django project. A normal POST/redirect/GET path remains canonical; HTMX requests return form, draw, and interpretation-status partials.

This fits the existing Django domain and avoids duplicating API contracts, auth state, and rendering logic in Next.js. A pure REST + SPA rebuild was considered, but it delays the core ritual and preserves the present integration mismatch.

### Anonymous ownership uses a random session principal

On the first journey interaction, create a high-entropy opaque identifier in the signed Django session. Persist it as an indexed owner field on anonymous readings, separate from the nullable user relation. Future account claiming attaches the authenticated user only after proving possession of that session; it does not mutate card records or reading IDs.

Using a public URL token was rejected because it is too easy to leak through history, screenshots, referrers, and Telegram messages. Requiring an account before a draw was rejected because it adds friction before the product demonstrates value.

### Spread definitions are versioned domain data

Represent launch spreads with an immutable key, ordered role labels, descriptions, and a content version. Start with single-card, three-card, Celtic Cross, career growth, and love choice after editorial review of the prototype definitions. Save a spread-version value with each reading so later copy changes do not rewrite history.

Hard-coding the full prototype decision matrix into prompts was rejected: the system needs predictable, reviewable behavior and manual spread selection is sufficient at launch.

### Deterministic draw is generated by the backend

When a reading is created, the service obtains a cryptographically strong per-reading seed, uses it to make a repeatable shuffle and orientations, then atomically stores all `ReadingCard` rows with roles. The seed is never exposed as a user-facing prediction mechanism. The saved rows, not replaying the random algorithm, are authoritative when a reading is reopened.

Simple `random.sample` without persistence was rejected because a retry could silently change the reading. Letting an LLM name cards was rejected because it causes hallucinated names and failed database mapping.

### AI produces validated structured interpretation only

Replace card-name output with a schema keyed by persisted `ReadingCard` IDs or positions, plus a concise overall reflection and optional follow-up prompt. Validate exact cardinality and identifiers before saving. The prompt declares reflection-only boundaries and high-stakes constraints. Status and provider-error metadata are persisted separately from display copy, allowing a retry using the same draw.

Free-form text was rejected because it is difficult to map and validate. Regenerating the whole reading on failure was rejected because it violates the ritual's continuity.

### Mentor content is product-owned and local

Introduce fields or related content records for locale, biography, visual description, style instruction, and managed media. Seed an editorially reviewed subset of `celestial-neutral` mentor personas and copy selected assets into Django static/media storage with provenance documented in the import command or fixture.

Retaining external avatar URLs was rejected because the current links are fragile and untrusted. Migrating every prototype persona before launch was rejected in favor of a small coherent catalogue.

### Telegram is a verified read-only adapter

The backend verifies Telegram Web App init data or a Bot API-compatible signed identity flow before issuing a scoped backend credential. The bot only reads public catalogue data and the caller's records. A later handoff may let a signed-in web visitor connect their Telegram identity.

Username-based lookup and a bot-local user database were rejected because both break ownership and permit impersonation.

## Risks / Trade-offs

- [Anonymous session loss strands a reading] -> Make loss explicit, offer account claiming after the journey, and do not promise recovery before identity exists.
- [AI latency makes the ritual feel stalled] -> Persist the draw immediately, display a distinct interpretation-pending state, and update the partial through a bounded asynchronous request.
- [Provider output violates schema or safety contract] -> Validate response IDs/cardinality and retain a failed state; never replace the stored draw.
- [Prototype content is inconsistent or unsuitable] -> Migrate only an editorially approved subset with local assets and locale review.
- [Telegram verification differs by channel UX] -> Keep launch bot read-only and treat web-to-Telegram linking as a follow-up capability.
- [Existing token deduction is non-atomic around provider failures] -> Include an explicit transactional accounting review before enabling any paid/quota behavior.

## Migration Plan

1. Rotate the exposed Telegram token and remove any remaining runtime dependency on it before deployment.
2. Add data migrations for anonymous ownership, draw metadata, spread version/status, and mentor content; retain nullable legacy relations during rollout.
3. Seed catalogue and launch mentor content in a staging database; validate local media and both locales.
4. Release public web catalogue and journey behind a feature flag, then enable draw persistence and interpretation after end-to-end verification.
5. Switch the Telegram bot to the documented read-only backend contract only after identity verification tests pass.
6. Roll back by disabling the journey/Telegram feature flags; persisted readings remain readable through the legacy API/admin and no card data migration is destructive.

## Open Questions

- Which model/provider and per-reading budget will be used for launch interpretation? The validation boundary and data model do not depend on that decision.
- Should English and Ukrainian launch with locale auto-detection, an explicit selector, or both? Either preserves the same reading and interpretation contract.
